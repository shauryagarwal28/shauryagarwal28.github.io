01 - The Problem

Group rides fall apart mid-route

India has over 10 million registered motorcycles, and group riding is a real, everyday habit, not a niche hobby. But once a group is moving at highway speed, there is no safe way for riders to stay in touch. Phone calls while riding are illegal under the Motor Vehicles Act, and genuinely dangerous even when they are not. So riders lose each other at junctions, split up without meaning to, and have no way to call for help if something goes wrong.

I wanted to see if I could actually solve this, not just write it up as a case study. So I designed and built Chalo myself, end to end: the product decisions, the screens, and the underlying app.

02 - Product Decisions

Two modes, one app

The first real decision was splitting the product into two modes, because the two use cases need almost opposite designs.

Active Ride Mode
For riders you already know
A private group of friends rides together right now. No sign-up friction, no verification. Live map, one-button push-to-talk, and automatic emergency detection if someone stops suddenly.
Community Mode
For riders you don't know yet
Discover public rides organised by verified strangers. This side needs trust, so it is gated behind KYC and a mutual rating system before anyone can join.

Why push-to-talk instead of a normal call: a live call needs both hands and full attention. Push-to-talk is a single button a rider can find by feel, and it fails safe: if nobody is talking, nothing happens.

Why a three-stage emergency flow: a sudden stop could mean a flat tyre or a real accident, and the app can't tell the difference right away. So it escalates gradually: a quiet banner to the group first, then a direct check-in to the rider who stopped, then a full alert to everyone only if there's no response within a minute. This avoids crying wolf on every red light while still catching real emergencies fast.

04 - A Real Problem I Had to Solve

When two pieces of code wanted the same name

Getting this running on Android surfaced a genuinely tricky bug, and I think it's worth including because it shows the kind of problem-solving a PM with technical depth can actually do, not just talk about.

The push-to-talk feature (Agora) and Android's build system both use a piece of internal plumbing that, it turned out, was accidentally sharing the same internal name as another required library. Android refused to build at all, because it couldn't tell the two apart.

There was no setting to fix this. I had to trace the conflict down to its source, then write a small build step that opens the problem library, quietly renames its internal identifier so it no longer collides, and repackages it before Android ever sees it. It's the kind of fix that isn't glamorous, but it's the difference between an app that only ever runs in a demo and one that actually builds and installs on a real phone.

05 - Current Status & What's Next

Honest about what's proven and what isn't

🔊 Push-to-talk audio needs a real phone

The code path is real and wired in, but simulators can't run real-time audio, so the actual "does it sound right" test still needs a physical device. That's next.

🧭 Community Mode isn't switched on yet

Deliberate sequencing, not a gap I missed: Active Ride Mode needs to be fully proven on real rides first, since it's the mode with no verification gate and the one people would use most.

Next up: a real highway test of push-to-talk, then wiring the backend fully into Active Ride Mode so a group can actually see each other move in real time, not just on one device.
